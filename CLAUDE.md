# terraform-provider-sparkpost

A Terraform provider for SparkPost, built on `terraform-plugin-framework` (not SDKv2). Single package: `internal/provider`.

## Repo layout

- `main.go` — entrypoint, `//go:generate` directive for docs.
- `internal/provider/` — everything: provider, resources, data sources, and the hand-rolled SparkPost HTTP client, all in one flat package.
  - `resource_*.go` / `data_source_*.go` — one file per Resource/DataSource implementation.
  - `client.go`, `domains.go`, `tracking_domains.go`, `subaccounts.go` — the API client. No framework types here; plain Go + `error`.
  - `import.go` — shared `parseImportID` helper (see Import below).
- `docs/` — generated by `tfplugindocs`, do not hand-edit.
- `examples/` — input to `tfplugindocs` (e.g. `import.sh` files render the "Import" section of a resource's doc page).

## Resource conventions

- Schema: framework `schema.Schema` struct literals (`resource/schema`, `datasource/schema`, `provider/schema`). Attributes that force recreation get `RequiresReplace()`; only add a real `Update` method for attributes that don't.
- Errors surfaced to Terraform go through `resp.Diagnostics.AddError(...)`, never a returned `error` from a CRUD method.
- Not-found handling: each client resource type has a sentinel (`ErrDomainNotFound`, `ErrTrackingDomainNotFound`) that the corresponding `Get*`/`Delete*` client function returns on a 404 (via `isNotFound(err)` in `client.go`, which checks the actual HTTP status `doRequest` returned, not string-matching). Resources check it with `errors.Is(err, ErrXNotFound)` in `Read()`, calling `resp.State.RemoveResource(ctx)`. Never compare sentinel errors with `==`, and never `strings.Contains(err.Error(), "404")` — that was the exact bug this repo used to have.
- `Read()` must refresh every attribute it can from the API response, not just check existence — Terraform can't detect drift otherwise. Check the actual JSON shape SparkPost returns (usually wrapped in `"results"`) before assuming a field round-trips; `sending-domains` GET doesn't echo `domain` back, `tracking-domains` GET does.
- Client functions wrap errors with context: `fmt.Errorf("...: %w", err)`. Delete should be idempotent — a 404 on delete means "already gone", not an error.
- Import: resources keyed on `(domain, subaccount)` implement `ResourceWithImportState` using the shared `parseImportID` helper — accepts `"domain"` or `"domain,subaccount"` as the import ID. Follow this pattern for any new composite-key resource rather than inventing another scheme. A resource keyed on a single server-assigned ID (e.g. `sparkpost_subaccount`) doesn't need `parseImportID` — just parse `req.ID` directly in `ImportState` and `SetAttribute` the typed value (an `Int64Attribute` `id` can't take `resource.ImportStatePassthroughID`'s raw string).
- Not every SparkPost resource has a real delete. `sparkpost_subaccount`'s `Delete()` calls `UpdateSubaccount(id, name, "terminated", ipPool)` — there is no delete endpoint, only a one-way `PUT .../subaccounts/{id}` status change (`active` → `suspended`/`terminated`; termination can't be undone via the API). Check a resource's actual API surface before assuming a DELETE verb exists.
- SparkPost's subaccount create endpoint (`POST /subaccounts`) only ever returns `{results: {subaccount_id, key, label, short_key}}` — never name/status/ip_pool, and it has no `status` field to set at creation time (new subaccounts always start `active`). `resource_subaccount.go`'s `Create()` therefore does create → `GetSubaccount` (to populate the rest of state) → an extra `UpdateSubaccount` call only if the plan asked for a non-`active` status. Don't assume a create response mirrors the resource's full schema; check the docs (`https://developers.sparkpost.com/api/subaccounts/`) for the actual response shape first.

## Docs

`go generate ./...` runs `tfplugindocs` (version pinned in the `//go:generate` line in `main.go` — deliberately not a `go.mod` tool dependency, since recent `tfplugindocs`/`terraform-plugin-testing` releases require Go 1.25+ and would drag the whole module's minimum Go version up just to run an occasional dev command; `go run pkg@pinned-version` avoids that). CI's "Docs up to date" job fails the build if `go generate` produces a diff — always run it after a schema or behaviour change and commit the result.

## Linting

`.golangci.yml` + `go run github.com/golangci/golangci-lint/v2/cmd/golangci-lint@<pinned>`. Same pinned-version-over-go.mod-dependency reasoning as docs. Gotcha: `go run pkg@version` builds golangci-lint against *its own* go.mod, ignoring this module's `toolchain` directive in `go.mod` — if that directive is ever bumped, the CI lint step's `GOTOOLCHAIN` env var in `.github/workflows/ci.yml` needs bumping to match, or golangci-lint refuses to run ("Go language version used to build golangci-lint is lower than the targeted Go version").

## Testing

- Unit tests (`*_test.go`, not `*_acc_test.go`) hit an `httptest.Server`, not the real API — always run, always safe.
- Acceptance tests (`TestAcc*`, in `*_acc_test.go`) hit a **real SparkPost account** and require `TF_ACC=1` + `SPARKPOST_API_KEY`. They create randomly-named domains (`tf-acc-test-<timestamp>.example.com` — inert, can't pass DNS verification, safe to leave stray) and destroy them as the final test step, but only cover `sparkpost_domain`/`sparkpost_tracking_domain` (the verification/association resources need a domain you actually control).
- Acceptance tests run only via the manually-triggered `.github/workflows/acceptance.yml` (`workflow_dispatch`), deliberately not on every push/PR — this hits production. Don't wire it back into `ci.yml`'s automatic triggers without a real reason.

## CI

- `ci.yml` (push to `main`, every PR): build/vet/unit-test, lint, docs-drift check. All safe, no live API calls.
- `acceptance.yml` (manual only): the live-account acceptance tests above.
- `release.yml` (tag push matching `v*` only): GoReleaser build, sign, publish. **Nothing releases on merge to `main`** — a release requires someone to push a tag.

## Releases

- `.goreleaser.yml` has `release.prerelease: auto` — a tag with a semver prerelease part (`v1.1.0-beta.1`, `v1.1.0-rc1`) is flagged as a GitHub prerelease automatically; a plain `vX.Y.Z` tag is a normal release.
- No changelog generation (`changelog.disable: true`) — write release notes by hand if you want them.
